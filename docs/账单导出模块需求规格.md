# 客户账单导出模块 需求规格

> **已确认决策（2026-08-22）**
> 1. 消费金额：**双列并出**（实际扣费 + 按公式重算）+ 差异列 + 计费类型列。
> 2. 「详细明细」sheet：**逐条请求日志**（最细粒度）。
> 3. 数据来源：**导出时实时回源库查**（不落快照）。
>    → 连带后果：导出耗时长，必须**后台生成 + 进度轮询**；且因为逐条明细本来就要
>      逐行捞回，**所有聚合改在 Python 里一遍过完成**，不在 SQL 里做 JSON 提取与 GROUP BY。
> 4. 倍率拆分：**全部计费倍率做「倍率指纹」**。

> 依据：`QuantumNous/new-api` main 分支源码（v1.0.0-rc.25，2026-08-18）逐文件核对，
> 关键事实均已二次证伪。标注「⚠️需实测」的为未在目标站点验证的部分。

## 0. 一句话结论

你的需求里 **7 条可以直接做**，**第 4 条（按单价重算消费金额）有硬性盲区**——
new-api 有 4~5 类日志用「单价×token×分组倍率」重算**必然对不上账**，必须先定口径。

## 1. new-api 事实基线（写 SQL 直接照抄）

### 1.1 `logs` 表

| 列 | 类型 | 备注 |
|---|---|---|
| `id` | bigint PK | |
| `user_id` / `username` | | 客户 |
| `token_id` / `token_name` | | **令牌维度，现有快照表完全没存** |
| `created_at` | **bigint（Unix 秒）** | 不是 datetime |
| `type` | int | **2=消费**，6=退款（quota 为正数但含义是退回） |
| `model_name` | varchar | 用户请求的原始模型名（定价也用它） |
| `group` | varchar | **MySQL 保留字**，必须 `` `group` ``；PG 用 `"group"` |
| `quota` | int | 实际扣费额度，USD = quota / QuotaPerUnit |
| `prompt_tokens` / `completion_tokens` | int | 语义见 §1.3 |
| `channel_id` | int | ⚠️ 列名 `channel_id`，但 HTTP API 里叫 `channel` |
| `channel_name` | varchar | ⚠️ **永远是空串**，需 JOIN `channels` |
| `other` | longtext | JSON 文本，见 §1.2 |
| `request_id` | varchar(64) | 有唯一索引，**增量导出用它做游标，不要用 id** |

索引：`idx_created_at_id(created_at, id)`、`idx_created_at_type(created_at, type)` —— 按时间范围扫是走索引的。

### 1.2 `other` JSON 里的计费字段（精确键名，全部已核实）

| 键 | 含义 |
|---|---|
| `model_ratio` | 模型倍率（按次计价时为 0） |
| `group_ratio` | **分组倍率，已经是最终生效值** |
| `user_group_ratio` | 用户组专属倍率，无专属时为 `-1`。⚠️ **命中时 `group_ratio` 已被它覆盖，绝不能再乘一次** |
| `completion_ratio` | 输出倍率 |
| `cache_tokens` / `cache_ratio` | **缓存读取** token 与倍率 |
| `cache_creation_tokens` / `cache_creation_ratio` | 缓存创建**总量**与倍率（Claude 默认 1.25） |
| `cache_creation_tokens_5m` / `cache_creation_ratio_5m` | 5m TTL，**仅非 0 时写入** |
| `cache_creation_tokens_1h` / `cache_creation_ratio_1h` | 1h TTL，**仅非 0 时写入**；倍率恒为 5m 的 **1.6 倍**，不可单独配置 |
| `image_output` | ⚠️ **名字叫 output，实际是输入图像 token**。配套 `image`(bool) / `image_ratio` |
| `audio_input_token_count` / `audio_input_price` | 音频输入（`audio_input_seperate_price`，注意拼写 seperate） |
| `model_price` | 按次单价（USD/次）；**按量计价时为 `-1`** |
| `usage_semantic` | **仅在 Anthropic 语义时写 `"anthropic"`**，其他语义该键不存在 |
| `tool_surcharges` | `[{name,count,price}]`，price 单位 **$/1K 次**。2026-07-26 前是 `web_search_call_count` 等旧键 |
| `billing_mode` = `tiered_expr` | 分层表达式计费，**倍率公式完全失效** |
| `billing_source` | `wallet` / `subscription`。订阅计费时 quota 照记但**钱包没扣** |
| `violation_fee` | 违规扣费日志，token 全 0 但 quota > 0 |
| `is_task` | 异步任务（MJ/视频），无 token |

> `other` 可能是空串或字符串 `"null"`（nil map 序列化结果），SQL 必须防御。

**「普通缓存创建」= `cache_creation_tokens − cache_creation_tokens_5m − cache_creation_tokens_1h`（钳零）。**
5m/1h 拆分只有 **Anthropic 语义**才有；OpenAI 语义下所有 cache write 统一用单一倍率。
且这两个键是 **2025-11-03** 之后的版本才有的，之前的历史日志没有。

### 1.3 ⚠️ `prompt_tokens` 到底含不含缓存 —— 分两套，必须分流

| 语义 | 判据 | 含 cache read | 含 cache write | 含 image |
|---|---|---|---|---|
| **Anthropic** | `other.usage_semantic == "anthropic"` | ❌ 不含 | ❌ 不含 | ✅ 含 |
| **OpenAI / Gemini** | 该键**不存在** | ✅ 含 | ✅ 含 | ✅ 含 |

有单测硬证据（`service/text_quota_test.go`）：Claude 上游 input=70/cache_read=30/cache_create=20 → `prompt_tokens == 70`；Gemini prompt=105 里**含** cached 7。

所以「输入 token（不含缓存）」：

```
Anthropic:  prompt_tokens − image_output − audio_input_token_count
其他:       prompt_tokens − cache_tokens − cache_creation_tokens − image_output − audio_input_token_count
两者结果都要 max(0, …)   ← new-api 自己也加了这个钳位
```

> 盲区：有一类 OpenAI 形状但按 Anthropic 口径计费的日志（`isLegacyClaudeDerivedOpenAIUsage`），
> 日志里**没有任何标记**。缓解办法：`cache_creation_tokens_5m/_1h` 存在也按 Anthropic 处理。

`completion_tokens` **包含** reasoning token，且 reasoning token 数**永远无法从日志拆出**。

### 1.4 完整计费公式（按量分支）

```
base = prompt_tokens
       − (非Anthropic时) cache_tokens + cache_creation_tokens
       − image_output                       ← 无条件
       − audio_tokens                       ← 仅 Gemini 音频独立计价时
base = max(base, 0)

cacheCreate = 非Anthropic: cache_creation_tokens × cache_creation_ratio
              Anthropic:   max(总量−5m−1h,0)×ratio + 5m×ratio_5m + 1h×ratio_1h

quota = ( base
        + cache_tokens × cache_ratio
        + image_output × image_ratio
        + cacheCreate
        + completion_tokens × completion_ratio ) × model_ratio × group_ratio
      + audio_input_price/1e6 × audio_tokens × group_ratio × QuotaPerUnit   ← 不乘 model_ratio
      × Π(otherRatios)                                                       ← ⚠️ 不落库，见 §1.6
      + Σ(tool.price × tool.count / 1000 × group_ratio × QuotaPerUnit)      ← 不乘 model_ratio

若 model_ratio×group_ratio ≠ 0 且结果 ≤ 0 → 强制 = 1     ← 最小计费 1 quota 地板
最后 Round(0) 四舍五入（不是向上取整），钳到 int32
```

按次分支（`model_price != -1`）：`quota = model_price × QuotaPerUnit × group_ratio`，**与 token 数无关**。

单位换算：`USD = quota / QuotaPerUnit`，QuotaPerUnit 默认 **500000**，
**是运行时可改的站点配置**（`options` 表 key = `QuotaPerUnit`，或 `GET /api/status` 的 `quota_per_unit`）。
派生单价：`$/1M tokens = model_ratio × 1e6 / QuotaPerUnit`（默认即 `model_ratio × 2`）。

### 1.5 模型单价存在哪 —— **没有历史版本**

- 只存在 `options` 表（两列 `key`/`value`），key：`ModelRatio` `CompletionRatio` `CacheRatio`
  `CreateCacheRatio` `ImageRatio` `AudioRatio` `ModelPrice` `GroupRatio` `GroupGroupRatio` `QuotaPerUnit`，
  分层 key `tool_price_setting.prices` / `billing_setting.billing_mode`。
- **没有** `pricing` / `model_prices` 表，**没有任何 history/version 表**，改倍率是就地覆盖。
- `options` 行不存在时生效的是**编译期默认表**（237 项 ModelRatio）；行存在时是**整体替换**语义。
- ⚠️ `CompletionRatio` 有**硬编码 locked 层**会**无视** options 配置：`claude-3*` / `claude-sonnet-4*` /
  `claude-opus-4*` / `claude-haiku-4*` → 恒为 **5**，`o1*`/`o3*` → 4，`gpt-5`(不含点) → 8 等。
  自己实现这套匹配极易出错。

**结论：重算历史账单只能用每条日志 `other` 里冻结下来的倍率，不能用「当前抓到的单价」。**

获取当前单价的最优路径（用于单价对照 sheet）：
`GET /api/pricing`（默认免登录，`completion_ratio` 已解析 locked 规则）+ `GET /api/status`（拿 `quota_per_unit`）。
次选直读 `options` 表（但要自带编译期默认表兜底）。

### 1.6 ⚠️ 无法重算的 5 类日志

| 类型 | 判据 | 原因 |
|---|---|---|
| 分层表达式计费 | `other.billing_mode == 'tiered_expr'` | quota 由表达式求值，与所有倍率无关 |
| 同步图像（n>1） | `request_path` 含 image | 张数乘数 `otherRatios` **不落库**，重算会偏低 n 倍 |
| 异步任务 / MJ | `other.is_task` | 无 token，按次计价 |
| 违规扣费 | `other.violation_fee` | token 全 0，quota > 0 |
| 渠道测试 | `token_name = '模型测试'` 且 `token_id = 0` | 是管理员测试，不该进客户账单 |

另有两类需要口径决策：
- **订阅计费**（`billing_source == 'subscription'`）：quota 照记但钱包没扣。
- **退款**（`type = 6`）：quota 是正数，语义是退回，需取负冲销。

## 2. 需求补全与澄清

### 2.1 消费金额的口径（**最关键**）

你要「按单价重算」，但由 §1.6，重算值和 new-api 实际扣费额在部分日志上**必然不一致**。

**建议方案：双列并出。**

| 列 | 来源 | 用途 |
|---|---|---|
| 实际扣费金额 | `SUM(logs.quota) / QuotaPerUnit` | **权威**，与客户站账面 100% 一致 |
| 重算金额 | 按 §1.4 公式逐条算 | 让客户看到「钱花在哪种 token 上」 |
| 差异 / 差异% | 两者之差 | 自动标红，暴露不可重算的日志 |

再加一列**「计费类型」**（按量 / 按次 / 分层 / 任务 / 违规 / 测试），让不可重算的行一目了然。
这样既不丢权威性，又满足「按单价拆解」的诉求。

### 2.2 ⚠️ 「周期内倍率变更要分开统计」必须扩大范围

你只提了分组倍率。但由 §1.4，`model_ratio` / `completion_ratio` / `cache_ratio` /
`cache_creation_ratio` 任何一个变了，聚合后再套公式都会算错。

**方案：聚合键里加「倍率指纹」** ——
`(model_ratio, group_ratio, completion_ratio, cache_ratio, cache_creation_ratio, cache_creation_ratio_5m, cache_creation_ratio_1h, image_ratio, model_price, usage_semantic)`。

指纹不同就是不同的行。倍率没变过时，一个模型仍然只有一行（不会平白多出行）；
变过就自动裂成多行，且每行的倍率都是真实生效值。**这比只盯分组倍率更正确，且不增加你的操作负担。**

### 2.3 账单粒度与 sheet 结构

主体：**客户站 × 客户(user) × 令牌 × 分组 × 模型 × 倍率指纹**。

| Sheet | 何时生成 | 粒度 |
|---|---|---|
| ① 账单汇总 | 总是 | 上述主体，周期内合计 |
| ② 按天明细 | 勾选「导出按天明细」 | 主体 **+ 日期** |
| ③ 详细明细 | 勾选「详细明细」 | **待确认，见问题 2** |
| ④ 模型单价 | 总是 | 周期内出现过的 (模型 × 倍率指纹) → 换算成各类 token 的单价 |
| ⑤ 说明 | 总是 | 周期、站点、QuotaPerUnit、口径说明、被排除的日志类型与条数 |

「调用次数」在 ①②④ 都有；③ 若是逐条日志则该列恒为 1（故你说的"非明细情况下"成立）。

### 2.4 导出列全集（可自定义顺序 / 改名 / 隐藏）

```
日期* / 站点 / 用户ID / 用户名 / 令牌ID / 令牌名 / 分组 / 模型名 / 计费类型
分组倍率 / 模型倍率 / 输出倍率 / 缓存倍率 / 缓存创建倍率
调用次数
输入token(不含缓存) / 缓存读取token / 缓存创建token-普通 / 缓存创建token-5m
缓存创建token-1h / 输出token / 图片token / 音频token / token合计
实际扣费金额 / 重算金额 / 差异 / 差异%
```
（`*` 仅按天明细 sheet 有）

### 2.5 模型单价 sheet 的表达

对每个 (模型 × 倍率指纹) 输出**基准单价**（未乘分组倍率）：

| 项 | 计算式 | 单位 |
|---|---|---|
| 输入 | `model_ratio × K` | 金额/1M tokens |
| 输出 | `model_ratio × completion_ratio × K` | 同上 |
| 缓存读取 | `model_ratio × cache_ratio × K` | 同上 |
| 缓存创建 5m | `model_ratio × cache_creation_ratio × K` | 同上 |
| 缓存创建 1h | `model_ratio × cache_creation_ratio × 1.6 × K` | 同上 |
| 图片输入 | `model_ratio × image_ratio × K` | 同上 |
| 按次 | `model_price` | 金额/次 |

其中 `K = 1e6 / QuotaPerUnit`（默认 2）。另加一列「分组倍率」和「客户实付单价 = 基准单价 × 分组倍率」。

## 3. 数据模型（新增）

现有 `customer_usage_daily` **完全不够用**：12 个目标列里 6 列缺失、1 列口径不足。
致命的是 `source.py:135` 在 SQL 层就写了 `SUM(prompt_tokens + completion_tokens) AS tokens`，
输入输出**已经被合并**，且没有令牌维度、没有任何 cache/image 字段。

**新增独立表**（不动现有利润链路，零回归风险）：

```python
class CustomerBillUsageDaily(Base):
    """客户站 日 × 客户 × 令牌 × 分组 × 模型 × 倍率指纹 的 token 明细（账单导出专用）。"""
    __tablename__ = "customer_bill_usage_daily"
    # 唯一键: stat_date, site_id, customer_id, token_id, group_name, model_name, ratio_key

    stat_date, site_id, customer_id, username, token_id, token_name,
    group_name, model_name, channel_id,

    ratio_key            : str    # 倍率指纹哈希，见 §2.2
    model_ratio, group_ratio, completion_ratio, cache_ratio,
    cache_creation_ratio, cache_creation_ratio_5m, cache_creation_ratio_1h,
    image_ratio, model_price      : float
    usage_semantic       : str    # 'anthropic' | ''
    billing_kind         : str    # usage|per_call|tiered|task|violation|test

    calls                : int
    input_tokens_ex_cache: bigint # 已按语义扣减，钳零
    prompt_tokens_raw    : bigint # 原始值，留作核查
    cache_tokens         : bigint
    cache_creation_plain : bigint # 总量 − 5m − 1h
    cache_creation_5m    : bigint
    cache_creation_1h    : bigint
    completion_tokens    : bigint
    image_tokens         : bigint
    audio_tokens         : bigint
    quota                : bigint # 实际扣费（权威）

```

配套：
- `export_column_config` 表（或 `app_setting` 存 JSON）：列顺序 / 自定义列名 / 是否导出。
  代码里维护列全集，DB 只存**覆盖项**；新增列自动按默认追加到末尾并默认显示 → 老配置不会失效。

## 4. 采集方案（不影响线上业务）

**沿用项目既有架构：落快照，导出只读本地。**

1. **日常**：现有 `save_snapshot` 追加一段，客户站每天多存一份 `customer_bill_usage_daily`；
   定时任务和「查询并保存」按钮自动带上。
2. **补历史**：新增「拉取指定周期」按钮，**按天逐日** + keyset 分页 + 批间 sleep 回源库补。
3. **导出**：只读本地快照，不碰源库 —— 月账单导出零压力。

源库 SQL 要点：
- 按 `created_at` 范围 + `id` keyset 分页（不用 OFFSET），每批 2000~5000 行，批间 `sleep(0.2~0.5s)`。
- MySQL：`SET SESSION max_execution_time`；PG：`SET LOCAL statement_timeout`。只读、短事务。
- JSON 提取防御（`other` 可能是 `''` / `'null'` / 非法 JSON）：
  - MySQL：`JSON_EXTRACT(IF(JSON_VALID(other), other, '{}'), '$.key')`
  - PG：`(NULLIF(other,'')::jsonb ->> 'key')`（PG 的 `''::jsonb` 会直接抛错，必须 NULLIF）
  - 整段包 try/except，失败降级到不带 JSON 列的版本（cache/image 记 0）而不是整天导出为空。
- 倍率指纹要在 `GROUP BY` 里，所以 JSON 提取会出现在 GROUP BY 中 —— MySQL 走不了索引，
  但有 `created_at` 范围先过滤，量级可控（3 站 × 100 日活，约 1 万行/天/站）。

排除规则（默认，可配）：`type = 2`、`token_id > 0`、`token_name <> '模型测试'`、
`other.violation_fee IS NULL`；`type = 6` 退款单独取负冲销。

实现过程中经源码核实修正的地方：

1. **音频 / Realtime(ws) 是第三套公式**，规格 §1.4 只写了文本链路。
   判据 `other.audio` 或 `other.ws`，公式见 `service/quota.go:calculateAudioQuota`：
   `(text_input + text_output×completion_ratio + audio_in×audio_ratio + audio_out×audio_ratio×audio_completion_ratio) × model_ratio × group_ratio`。
   已单独识别并按该公式重算，音频量单独进「音频token」列。

2. **倍率指纹只用无条件写入的键**（`model_ratio` / `group_ratio` / `completion_ratio` /
   `cache_ratio` / `model_price` + 语义 + 计费类型）。
   `cache_creation_ratio` / `_5m` / `_1h` / `image_ratio` 是**按需写入**的，放进指纹会让
   「这次没建缓存」和「这次建了缓存」拿到不同指纹、同一价格平白裂成多行。
   它们改为「展示用」，在桶内取第一个非零值补齐。

3. **QuotaPerUnit 逐站读取**（源库 `options` 表 key=`QuotaPerUnit`），不能用本系统全局值 ——
   它是每个站点各自可改的配置，多站导出时一个标量在数学上不可能同时正确。
   金额列与「模型单价」sheet 都用各自站点的值，说明 sheet 逐站列出。

4. **`hasBillableUsage` 归零对按次也生效**（`text_quota.go:378` 在两个分支之外），
   且判据只看原始 `prompt_tokens + completion_tokens`，不含 cache/image/audio。

5. **任务链路有三种写日志姿势**：`LogTaskConsumption` 写 `is_task`；
   `RefundTaskQuota` / `RecalculateTaskQuota`（差额结算，也是 type=2）只写 `task_id`。
   判据改为 `is_task or "task_id" in other`。

6. **取整用纯 Decimal `ROUND_HALF_UP` + int32 钳位**，先转 float 会在 `.5` 边界比 Go 多进 1。

7. **计费类型新增** `audio`（音频/实时）与 `nodata`（无倍率信息，`other` 损坏或无 `model_ratio`）。
   后者不假装能重算，重算金额直接采信实际扣费。

运行约束：
- 同时最多 **2 个**导出任务（读的是线上库）；超出直接拒绝并提示。
- 临时文件统一在 `<tmp>/billexp/`，进程启动时清残留；完成的任务 **6 小时** TTL、最多保留 20 个。
- 任一 sheet 超过 Excel 单表上限自动分表（`账单汇总2`、`详细明细2`…）——
  XlsxWriter 在超限时是**静默丢弃**且 autofilter 会写出越界 ref 让 Excel 报损坏。
- 异常信息里的源库 DSN 会脱敏后再落到页面与日志。

已知盲区（无法从日志恢复，靠「差异」列暴露）：
- 图像 `n>1` 的张数乘数 `otherRatios` 不落库，这类请求重算会偏低；
- 分层表达式计费的 quota 与所有倍率无关；
- reasoning token 数量 new-api 从不写入日志，无法从「输出token」里拆出。
